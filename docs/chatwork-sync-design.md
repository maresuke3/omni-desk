# データ取得・送信の設計（Chatwork を中心に）

## 前提（想定する規模）

| 項目 | 値 |
| --- | --- |
| Chatwork の取引先ルーム | 約 700（取引先 約 675 社＋社内） |
| 毎日動くルーム | 約 340 |
| 30 秒間に変化するルーム | 平常時 20、ピーク時 40〜50 |
| 担当者 | 6 名（各自のアカウントでアプリを使う） |

Chatwork API の制約（公式ドキュメントで確認済み）:

- 全体で **5 分あたり 300 回**（応答ヘッダー `x-ratelimit-limit` / `remaining` / `reset`、超過時は 429）
- メッセージ取得は 1 回で**最新 100 件まで**、ページングなし
- 投稿・タスク作成は**ルームごとに 10 秒あたり 10 回**（上の 300 回とは別に適用）
- Webhook は画面からのみ作成でき、**1 アカウント 5 件まで**。再送はなく、エラーが多いと自動で無効化される
- 自分宛てを直接返す API や、ストリーミング API はない

> 1 アカウントで使えるのは「およそ 1 秒に 1 回」。毎分 90 ルームが動く環境で全ルームの本文をリアルタイムに
> 取ることは、ポーリングでも Webhook でも不可能。**「全ルームの変化は安く検知し、本文は必要なものだけ取る」**ことが設計の前提。

## 全体像

```
 ┌──────────────── メインプロセス ────────────────┐        ┌──── レンダラー ────┐
 │  ChatworkSync / SlackSync（同期エンジン）        │ state  │  Zustand ストア     │
 │    ├─ 変更検知（ルーム一覧を 30 秒ごと）          │ :patch │   ├ services       │
 │    ├─ 優先度付きキュー（Scheduler）              │ ─────▶ │   ├ histories      │
 │    └─ 予算管理（RateGovernor）                   │        │   ├ ui / drafts    │
 │  StateHub（状態の正。差分を seq 付きで送る）      │ ◀───── │   └ outbox         │
 │  暗号化ストレージ（自分宛て・ルームの状態）        │ invoke │  画面（Feature）    │
 └───────────────────────────────────────────────┘        └───────────────────┘
```

- API を呼ぶのはメインプロセスだけ。画面（レンダラー）は Zustand ストアを読むだけで、API 回数に影響しない。
- 1 アカウントの読み取り・送信・タスク操作は、**すべて同じ優先度付きキューと予算**を通る。

## 優先度と予算（`connectors/core/src/scheduler.ts`）

| 優先度 | 用途 | 実行条件（5 分あたり） |
| --- | --- | --- |
| 0 write | メッセージ送信・タスク操作 | 残り 1 回以上あれば実行（最後まで残す） |
| 1 view | 画面で開いている会話の取得 | 残り 15 回超・使用 285 回未満 |
| 2 mention | 自分宛ての未読が増えたルームの取得 | 同上 |
| 3 poll | 変更検知（ルーム一覧） | 残り 30 回超・使用 270 回未満 |
| 4 tasks | タスク一覧の更新 | 残り 40 回超・使用 240 回未満 |
| 5 backfill | 起動時・スリープ復帰時の追いつき | 残り 80 回超・使用 180 回未満 |
| 6 scan | 自分宛ての未読が増えなかった変化ルームの確認 | 残り 100 回超・使用 150 回未満 |

- 「残り」はアプリ内で数えた回数と、応答ヘッダーの `x-ratelimit-remaining` の小さい方。
- 429 を受けたら `x-ratelimit-reset` までキュー全体を止める。
- 同じルームの取得は 1 つにまとめる（何度変化しても、取りに行くのは 1 回）。

## 読み取り

### 変更検知（30 秒ごと、5 分で 10 回）

ルーム一覧（`GET /rooms`）は 1 回で全ルームの「最終更新時刻・メッセージ数・未読数・自分宛ての未読数・自分のタスク数」を返す。
前回の値と比べ、変化に応じて次のように扱う（`connectors/chatwork/src/sync.ts` の `planRoomFetches`）。

| 変化 | 扱い |
| --- | --- |
| 自分宛ての未読数が増えた / DM の未読数が増えた | mention で本文を取得 |
| 画面で開いているルームが変化した | view で本文を取得 |
| 起動時・復帰時の追いつき中に変化していた | backfill で本文を取得（余裕のあるときだけ） |
| それ以外の変化 | scan で取得（最低優先度。予算に余裕があるときだけ） |
| 自分のタスク数の合計が変わった | タスク一覧を取得 |

### 見積もり（あなた宛てがピーク時 5 分 10 件、画面で開くルームが 5 分 10 件と仮定）

| 状況 | 5 分あたりの回数 |
| --- | --- |
| 平常時（30 秒に 20 ルームが変化） | 約 30 回（変化したルーム数にはほぼ比例しない） |
| ピーク時（30 秒に 45 ルームが変化） | 約 30 回 |
| 起動直後の追いつき | backfill は 180 回で頭打ち。残りは次の枠へ |

### 自分宛てメッセージの保存

- 取得したメッセージのうち、自分宛て（To / 返信 / 全員宛て）と DM を「自分宛て一覧」に統合する（同じ ID は新しい内容で置き換え）。
- 直近 14 日・最大 500 件を、OS の暗号化ストレージで暗号化して保存する（`userData/sync/chatwork-<アカウントID>.bin`）。
- 次回起動時は保存済みの一覧をすぐ表示し、その後に差分を取る。接続を解除したら削除する。

### scan（取りこぼし対策）

自分宛ての未読数は Chatwork 側で読むと減るため、「増えたルームだけ取る」方式では、30 秒以内に Chatwork で読まれた自分宛てを取りこぼす。
（Chatwork の画面を開きながら使う運用では頻繁に起きる。）そこで、自分宛ての未読数が増えなかった変化ルームも最低優先度の scan で取得する。

- 他の取得や送信のために、5 分あたり 150 回までに抑え、残り 100 回を切ったら止める
- 同じルームが何度変化しても取得は 1 回にまとまる（ピーク時は数分遅れて追いつく。「漏れ」が「遅れ」に変わる）
- 取得したルームに自分の返信（返信タグ）があれば、受信箱の該当メッセージを対応済みにする

### 既読状態

Chatwork はメッセージ単位の既読を返さないため、取得時のルームの未読数から「新しい方から未読数ぶん」を未読とみなす。
変更検知でルームの未読数が 0 になったら、そのルームの自分宛てを既読にする。

### 既知の制約

- 自分宛ての未読数が増えてから 30 秒以内に Chatwork 側で既読にされた場合は、scan で取得されるまで（ピーク時は数分）受信箱に出ない。
- 起動時に 100 件以上たまっていたルームは、古い分を取得できない（API の仕様）。
- 自分宛て以外の本文は、ピーク時は開くまで最新にならない。「未対応の問い合わせ一覧」を作る場合は backfill と同じ低優先度で取得し、数分遅れで更新される一覧になる。

## 送信（返信・投稿）

- `POST /rooms/{room_id}/messages`（フォームで `body` と `self_unread=0`）。優先度 0（write）で、ほかの取得より先に実行する。
- ルームごとの「10 秒 10 回」は、送信前にアプリ内で待って守る。
- 返信は Chatwork の画面と同じ形式の返信タグを付ける: `[rp aid={相手} to={ルーム}-{メッセージ}]{名前}さん` ＋改行＋本文。
- 送信後は画面にすぐ反映し、開いている会話なら正式な内容を取り直す（1 回）。
- 画面側では下書きと送信状況を Zustand（drafts / outbox）に置く。失敗時は下書きを残し、再送信できる。同じ入力欄からの二重送信は防ぐ。

Slack は `chat.postMessage`。チャンネルではスレッドに返信し、DM・グループ DM では元がスレッド内のときだけスレッドに返す。
ユーザートークン方式では、Slack アプリに `chat:write` 権限が必要（`docs/slack-app-manifest.yml` に追加済み。既存のアプリは再インストールが必要）。

## 受信箱の対応状況

- 未対応 / あとで（指定時刻まで隠す）/ 対応済み の 3 状態。PC の `userData/inbox-state.json` に、メッセージ ID・状態・時刻だけを保存する（本文は保存しない）。30 日で消える。
- 返信すると自動で対応済み（アプリから返信した場合・Chatwork で返信タグ付きで返信していた場合）。
- 設定「対応済みにしたら、サービス側も既読にする」が ON のとき:
  - Chatwork: `PUT /rooms/{room_id}/messages/read`（`message_id` まで既読。ルーム単位なので、それより前の未読もまとめて既読になる）。優先度は write
  - Slack: `conversations.mark`。ユーザートークン方式では channels:write / groups:write / im:write / mpim:write の権限が必要
  - 既読化に失敗しても対応済みにはなる（画面に警告を出す）

## タスク（今後の操作を含む）

| 操作 | API | 優先度 | 備考 |
| --- | --- | --- | --- |
| 自分のタスク一覧 | `GET /my/tasks?status=open` / `done` | 4 tasks | タスク数の合計が変わったとき＋10 分ごと |
| 完了・未完了に戻す | `PUT /rooms/{room_id}/tasks/{task_id}/status`（`body=done/open`） | 0 write | **未実装**。実行後に一覧を 1 回取り直す |
| タスクを作成 | `POST /rooms/{room_id}/tasks`（`body`、`to_ids`、`limit`、`limit_type`） | 0 write | **未実装**。投稿と合わせて 10 秒 10 回の制限を受ける |

タスク操作を実装するときは、送信と同じく `ChatworkSync` に操作を足し、`ChatworkApi.put/post` を write の優先度で呼ぶ。
画面ではタスク行に操作中・失敗の状態を表示し、ストアの tasks は同期エンジンからの差分で更新する（画面から直接書き換えない）。

## Slack の今後

Slack には Chatwork のような「全会話の変化を 1 回で取れる」公開 API がないため、当面は設定の間隔ごとに取得している。
本番運用では Socket Mode（Events API を WebSocket で受信する。公開 URL は不要）への置き換えを検討する。
ただし正式な Slack アプリが必要で、To-dos 用のブラウザセッション方式とは併用になる。

## 実装前・運用前に実機で確かめること

1. 同じルームに `force=1` を 30 秒間隔で呼べるか（非公式情報に「5 分に 1 回程度の制限」の記述がある）
2. ルームの更新時刻・メッセージ数が、編集・削除・タスク追加・既読などで変わるか
3. メッセージを取得しただけで既読にならないか
4. 自分宛ての未読数が To・返信・全員宛てを数えるか
5. 上限の単位（トークン単位か、アカウント単位か）。429 になったリクエストも回数に数えるか
